# 审计容量、可用性与有限限制动作预留

仍为单体 SQLite，未改审计存储格式、事务认证链或归档协议。持久审计不会静默
覆盖/丢弃；内存 ring 的既有可淘汰行为单独保留。

## 状态不是累计序号

`AuditStatus`、管理状态 API、CLI 审计输出及管理页面新增以下信息：

- `retained`：当前保留记录。持久模式为 sequence-base，归档后的累计序号不能
  当成占用；内存模式为当前 ring 长度。
- `reserved`：已准入在途操作的终态预留数，与旧 `pending` 一致。
- `remaining`：物理容量扣除当前记录及终态预留后的剩余槽，最低为零。
- `restriction_reserve`：配置的限制动作预留；`regular_remaining` 是普通写入
  上限再扣除记录及终态预留后的剩余槽，最低为零。
- `operation_ready`：审计容量允许开始一个需要开始+终态两条记录的新操作，
  且不是关闭、审计故障或离线维护状态。**不代替身份、策略或下游健康检查。**
- `restriction_ready`：审计存储允许再提交一条限制记录，且未关闭/故障。
  **不保证某个动作有权限、CAS 版本匹配或确实减少权限。**

`healthy` 仍仅表示未检测到审计存储故障；可以 healthy=true 而 operation_ready=false。
存储故障或未知提交后，计数只是最后确认的内存视图，不证明磁盘最终状态；须重开核对。
管理页面在业务审计准入不可用时明确提示，而不是仅展示容量总数。限制动作也
不可用时提示受信离线归档/停服维护，失败不表示撤权已持久化。

内存 ring 满后继续淘汰旧记录，因此 remaining=0 也可 ready=true；必须结合
persistent 与 dropped 解读。不要将它当成不丢日志的持久模式。

## 显式、有限、全局的预留

管理员可在启动配置中选择，例如：

```json
"audit": { "capacity": 4096, "restriction_reserve": 16 }
```

默认 restriction_reserve=0，保留此前容量行为，**默认不提供额外紧急空间**。
预留必须非负；启用时至少给普通操作保留两槽。它只限制持久模式的普通准入，
不是增加存储容量，不会删除已有记录或把已满数据库变空；对已接近满的数据库
新增预留可能立即停止普通业务，需先评估状态及受信离线归档。

普通调用/发现、扩权、换凭据、创建用户、配置应用和普通维护使用
capacity-restriction_reserve 的上限。开始业务操作时仍一次预留开始+终态两条。
所有路径均不能借用已有在途终态槽。

以下**实际权限减少**可用剩余物理容量：

- 活跃绑定首次转为 revoked 并清空凭据；
- 未禁用身份首次禁用；
- 白名单集合严格缩小，没有添加任何新名称；
- 通过原管理确认票据或离线维护接口，尚未 revoked 的入口凭据首次撤销。

只推进版本、重复撤销/禁用、重排/重复白名单或等价集合不能使用预留。重复动作
继续原有 CAS 和审计规则，不冒充幂等成功；有普通容量时仍可能记录，普通容量
不足则返回容量错误。先前 stale expected 仍是版本冲突，不自动重试。

预留是整个实例共用的有限空间，合法限制动作也可能耗尽它。耗尽后操作明确失败，
不绕过审计、不偷偷执行仅内存撤权、不报告持久成功。应停止新的业务并按受信
维护/归档流程处理，不能靠反复重启、删库或重新初始化来恢复容量。

## 持久提交和未知结果

限制状态与对应审计记录仍在同一 SQLite 事务提交，成功后才发布内存状态、失效
目录并尽力取消旧操作。取消不等于远端回滚。提交故障封闭当前实例；提交回执
丢失时事务可能已提交，调用方仍得到错误，必须重开并核对认证后的权威状态，
不得从错误推断“撤权一定没发生”或自动重复提交。

测试在预留区内分别注入事务回滚和真实提交后回执丢失，核对返回错误、不发布
未经确认的内存候选、实例停止准入，以及重开后状态/事件同时不存在或同时存在。
另覆盖终态预留不被限制动作占用、重复/扩权拒绝、预留耗尽、首次禁用/在线及离线撤入口、
归档后重新计数、内存 ring 与管理页面警示。均为合成数据，不是生产容量测量。
